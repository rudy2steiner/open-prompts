# 用户与管理后台缓存及异步刷新设计

## 背景

Open Prompts 当前由 `SessionProvider` 在客户端重新读取登录状态。发生整页导航或重新挂载 Header 时，`useSession()` 会短暂处于 `loading` 或未认证状态，已登录用户可能先看到 `Sign in`，随后才显示头像。

用户 Billing 和管理后台主要由服务端同步查询后一次性输出。Tab、页码或后台模块切换时会重复等待同类查询；部分客户端列表刷新前会进入空白或 loading 状态。AirAPVideo 已采用“浏览器账户快照、服务端短 TTL 缓存、旧值优先并后台刷新”的组合方式，本设计在不降低权限隔离的前提下将该模式应用到 Open Prompts。

## 目标

- 已登录用户切换站内页面时，Header 不再短暂显示登录按钮。
- 用户 Billing 和管理后台切换已访问过的 Tab、页码或筛选条件时，优先显示最近一次数据。
- 缓存过期后仍可立即返回旧数据，并在后台异步刷新。
- 刷新失败时保留已有内容并提示数据可能未更新，不把表格清空。
- 写操作完成后使相关缓存失效，尽快显示更新结果。
- 用户、订单、额度和管理数据保持严格的账户与权限隔离。

## 非目标

- 不使用缓存绕过 NextAuth、管理员权限或 API 权限校验。
- 不把订单、额度、用户列表等敏感数据放入公共 CDN 缓存。
- 不引入 Redis、外部缓存服务或新的数据请求框架。
- 不改变现有后台信息架构、表格字段、分页规则或业务权限。
- 不承诺多个 Worker 实例之间实时共享内存缓存；数据库仍是唯一事实来源。

## 总体方案

采用三层缓存：

1. Header 账户展示快照：浏览器 `sessionStorage`，仅保存首屏展示所需的最小用户信息。
2. 后台页面客户端快照：组件生命周期内的按键缓存，用于 Tab、分页和筛选条件切换；不持久化完整敏感列表。
3. 服务端短 TTL 缓存：进程内 stale-while-revalidate，用于重复的只读后台查询。

所有 API 继续执行真实身份校验。缓存命中只减少等待和数据库查询，不改变授权逻辑。

## Header 账户快照

新增独立的浏览器账户快照模块，避免把缓存细节散落在 Header 中。

快照字段仅包含：

- `userId`
- `name`
- `email`
- `image`
- `isAdmin`
- `balance`（可空）
- `updatedAt`

缓存键包含版本号，例如 `open-prompts:account:v1`。缓存只写入 `sessionStorage`，关闭浏览器 Tab 后自然消失。

Header 初始化流程：

1. 服务端输出保持稳定的 Header 容器尺寸。
2. 客户端使用 `useLayoutEffect` 在首次绘制前读取快照。
3. `useSession()` 为 `loading` 时，如果存在快照则显示缓存头像；不存在快照则显示等宽骨架，不显示 `Sign in`。
4. NextAuth 返回已认证 session 后，以真实 session 更新展示和快照。
5. NextAuth 明确返回未认证后，清除快照并显示登录按钮。
6. 登出时先清除快照，再执行 NextAuth `signOut`。

安全边界：缓存头像可用于视觉连续性，但管理员菜单和任何写操作最终仍以当前 NextAuth session 与服务端权限校验为准。如果缓存标记为管理员而真实 session 尚未确认，管理入口不提前显示。

## 用户 Billing 页面

保留服务端加载当前 Tab 首屏数据并传给客户端的模式，保证首次进入即可看到真实内容。将 `AccountBilling` 调整为可交互的客户端视图：

- 缓存键：`userId + tab + page`。
- 服务端传入的首屏数据直接写入当前缓存项。
- 已访问 Tab 或页码再次打开时立即显示缓存数据，同时请求最新数据。
- 未访问页面显示稳定骨架，不显示错误的零余额或空列表。
- 刷新时保留旧表格，并以轻量状态标记“正在更新”。
- 请求失败且已有缓存时保留缓存并显示非阻断提示；无缓存时显示正常错误状态。
- 用户 ID 改变或登出时清空全部 Billing 客户端缓存。

Billing API 响应使用 `private, no-store`，防止浏览器 HTTP 缓存或共享代理复用用户数据。前端展示缓存由应用自行管理。

## 管理后台页面

### 服务端查询缓存

新增通用的进程内 stale-while-revalidate 缓存，缓存项包含：

- `value`
- `freshUntil`
- `staleUntil`
- `refreshing` Promise

读取规则：

- 无缓存：等待数据库查询，成功后写入缓存。
- 新鲜期内：立即返回缓存。
- 已过新鲜期但仍在 stale 期：立即返回旧值，并且最多启动一个后台刷新请求。
- 超过 stale 期：等待刷新；失败时由调用方处理错误，不无限返回过旧数据。

默认时间：

- 管理汇总：fresh 30 秒，stale 5 分钟。
- 用户、生成记录、事件列表：fresh 15 秒，stale 2 分钟。
- 模板审核、管理员用户列表及趋势数据：fresh 15 秒，stale 2 分钟。
- 用户 Billing 数据不进入跨用户服务端缓存，继续按当前用户实时查询并使用客户端页面缓存。

缓存键必须包含影响结果的全部参数：数据域、Tab、页码、页大小、搜索词、状态筛选、趋势天数。管理数据仅在通过管理员权限校验后读取缓存。缓存值本身不包含授权结论。

### 客户端切换体验

管理后台列表使用页面生命周期缓存：

- 缓存键与服务端查询键保持一致。
- Tab、分页或筛选切回已访问状态时立即展示旧数据。
- 后台刷新期间不清空列表。
- 使用 generation token 或 `AbortController` 防止较慢的旧请求覆盖新筛选结果。
- 失败时保留旧数据；只有没有任何可展示数据时才进入完整错误态。

## 缓存失效

所有会改变后台只读结果的操作必须在成功后失效相关缓存：

- 用户额度调整：失效用户汇总、用户列表、Billing 汇总和额度流水。
- 模板审核、删除、批量操作：失效模板列表、审核数量和相关汇总。
- 订单或订阅状态变化：失效 Billing 订单、额度汇总和管理订单汇总。
- 生成任务完成或退款：失效生成记录、额度汇总和管理汇总。

服务端失效采用命名空间或前缀删除，避免依赖完整枚举所有分页键。客户端写操作成功后直接更新当前可确定的数据，并触发相应查询异步刷新。

在无共享缓存的多实例环境中，失效只影响当前实例，因此短 TTL 是最终一致性的兜底。数据库始终是权威数据源。

## 错误处理与可观测性

- 后台刷新失败不会删除可用旧值。
- 首次加载失败仍显示明确错误与重试入口。
- `AbortError` 不作为用户可见错误。
- 服务端后台刷新捕获异常，避免未处理 Promise；记录缓存命名空间和刷新失败原因，不记录敏感响应内容。
- 可通过开发环境调试信息区分 `miss`、`fresh`、`stale` 和 `refresh`，生产 UI 不展示内部缓存状态。

## 测试策略

### 单元测试

- Header 快照的校验、读取、写入、过期与清除。
- `loading + 有缓存用户` 显示头像且不显示登录按钮。
- `loading + 无缓存` 显示稳定占位。
- NextAuth 明确未认证后清除快照。
- stale-while-revalidate 的 miss、fresh、stale、并发去重、过期和刷新失败行为。
- 缓存键包含全部查询条件。
- 写操作后的前缀失效行为。

### 组件测试

- Billing 切回已访问 Tab 立即显示旧数据并触发刷新。
- 刷新期间旧表格不消失。
- 有旧数据时刷新失败不会清空内容。
- 管理后台快速切换筛选时旧请求不能覆盖新结果。

### 集成验证

- 已登录用户在首页、Billing、管理后台间切换，Header 始终保持头像。
- 管理员切换 Users、Generations、Events 时可立即看到缓存内容并异步更新。
- 普通用户无法读取任何管理缓存对应的 API。
- 登出再登录另一个账号后，不显示前一个账号的 Header 或 Billing 数据。
- 完整测试、TypeScript 检查和生产构建通过。
