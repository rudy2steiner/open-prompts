# 首屏性能优化设计

## 1. 背景

当前生产版本已经修复主导航在 hydration 前点击导致的白屏问题，但核心页面在正式域名下仍明显慢于同一 Worker 的 `workers.dev` 域名。现有实测表明，两者运行相同版本、返回相同静态资源，主要差异来自正式域名在当前中国大陆网络中的跨境访问链路：正式域名的 HTML 首字节可能达到数十秒，静态 JavaScript 也存在数秒乃至超时，而 `workers.dev` 通常在数秒内完成。

代码仍有可观的优化空间：部分页面初始 HTML 过大，根布局承担了过多全局客户端状态，导航栏、弹窗、国际化消息及非首屏功能扩大了 hydration 范围。尤其创建页解码后的 HTML 约 3.49 MB，首页、列表和详情页约 0.4–0.5 MB。即使无法消除跨境网络延迟，也应确保 HTML 一旦到达便立即呈现可用内容，并显著减少后续脚本下载、解析和 hydration 的成本。

## 2. 目标

本次优化以“HTML 到达后首屏立即可用”为核心目标：

- 首页、图片提示词列表、动画提示词列表、详情页、定价页和创建页在客户端 JavaScript 未加载时仍能显示主要内容。
- 导航在慢网和 hydration 前不会清空当前页面或出现白屏。
- 将创建页初始 HTML 解码体积降至 500 KB 以下，将其余核心页面降至 200 KB 左右；若个别页面因结构化数据等必要内容无法达到，应在验收记录中说明原因且不得超过 300 KB。
- 将核心路由首屏必须下载的 JavaScript 压缩体积控制在 150 KB 以内；按需功能不计入首屏预算。
- 在 `workers.dev` 基准链路中，核心页面冷启动可见时间目标不超过 3 秒、热缓存目标不超过 2 秒。
- 保持登录、会话、余额、单次购买、订阅、微信支付、OAuth 和 Stripe webhook 行为不变。

上述时间指标用于衡量应用自身回归，不承诺正式域名在中国大陆任意网络中“绝对秒开”。正式域名的 HTML 首字节仍受跨境路由、运营商和 Cloudflare 节点调度影响。

## 3. 非目标

- 本次不接入 EdgeOne、境内 CDN 或其他备用域名。
- 不调整 DNS、域名备案方案和 Cloudflare 区域路由。
- 不重写为传统多页应用，也不移除 React 或 Next.js。
- 不修改定价、支付币种、微信支付展示规则和 Stripe 账户配置。
- 不在正式环境完成真实扣款；正式环境仅验证收银台能正常打开。

## 4. 设计原则

### 4.1 服务端内容优先

页面的标题、正文、卡片、SEO 元数据和首屏图片由 Server Component 生成。客户端组件只负责确实依赖浏览器状态的局部交互，不能为了一个按钮或弹窗把整棵页面树变为客户端组件。

### 4.2 小型客户端孤岛

全局导航拆为稳定的服务端骨架和少量客户端孤岛：

- Logo、主导航链接、语言无关的静态结构由服务端渲染。
- 登录状态、头像、余额和退出操作放入独立的账户孤岛。
- 登录、下载、生成等弹窗仅在用户触发时动态加载。
- 主题、语言切换等必须交互保留为独立的小组件，不扩大父级 hydration 范围。

### 4.3 首屏数据最小化

服务端只向初始 HTML 发送当前视口和首屏渲染需要的数据。大列表、编辑器配置、历史记录、后台能力和弹窗数据在滚动、空闲或用户操作后加载。服务端已经使用的数据不得再次以大对象形式序列化到客户端。

### 4.4 个性化边界清晰

公共页面主体保持可缓存，登录态和余额通过小型动态区域获取。不得因为全局 `SessionProvider` 或用户查询使整页失去静态生成、边缘缓存或流式输出能力。

## 5. 总体架构

请求到达后，Next.js/Worker 先返回公共页面的服务端 HTML。浏览器可立即展示导航、标题、首屏卡片和主要操作。随后只有账户区、筛选控件等局部客户端孤岛进行 hydration。非关键弹窗和复杂功能模块在用户操作后才下载。

数据边界如下：

1. 路由服务端组件读取语言、路由参数和公共数据，生成可缓存 HTML。
2. 首屏所需的精简数据以组件属性传入；完整记录保留在服务端。
3. 账户孤岛单独读取会话，并只返回展示头像、余额和登录态所需字段。
4. 用户点击登录、下载、购买或创建功能后，再加载对应客户端模块和接口数据。
5. hydration 未完成时，现有导航保护逻辑保留当前页面；客户端就绪后继续目标导航。

## 6. 分阶段改造

### 阶段 0：建立性能基线和预算门槛

- 固化核心路由清单及正式域名、`workers.dev` 两条测量链路。
- 记录 HTML 解码体积、首屏 JavaScript 压缩体积、TTFB、FCP、LCP、DOMContentLoaded 和 hydration 完成时间。
- 增加构建产物体积检查，超过预算时在验证阶段直接失败。
- 保留慢速脚本和完全禁用 JavaScript 两类浏览器测试。

### 阶段 1：拆分全局布局与导航

- 将导航静态部分转换为 Server Component。
- 将账户信息、主题和语言切换拆为互不影响的小型客户端孤岛。
- 移除不必要的根级客户端包装；确实依赖会话的组件就近挂载 provider。
- 登录及下载弹窗改为点击后动态导入，并提供轻量加载状态。
- 保留现有 `Link` 导航、pending 状态和 hydration 前导航保护。

### 阶段 2：缩小国际化与全局 Provider 范围

- 仅向客户端组件传递其实际使用的国际化消息，不把完整语言消息树序列化到每个页面。
- 静态文案尽量在服务端完成翻译。
- 审核根布局的 Session、主题、通知和分析 provider，将非全局依赖下沉到实际消费位置。
- 确保中文页面的微信支付按钮规则不因消息拆分发生变化。

### 阶段 3：逐页削减初始负载

按创建页、详情页、列表页、首页、定价页的顺序处理：

- 创建页仅输出首屏表单骨架、必要默认值和首个可见区域；模型清单、高级配置、历史记录等按需加载。
- 详情页只序列化当前记录和首屏相关推荐，后续推荐延迟加载。
- 列表页减少初始卡片数量，翻页或无限滚动数据不进入首屏 HTML。
- 首页只保留首屏展示需要的精选内容，其余区块在视口接近时加载。
- 定价页保持服务端可见的方案结构；支付 SDK 和收银台逻辑仅在用户点击购买后加载。

### 阶段 4：图片、分析与非关键任务延后

- 明确首屏关键图片并设置正确尺寸与优先级，非首屏图片统一懒加载。
- 避免一次性预加载大量卡片图片或字体。
- 分析、统计和非关键埋点在首屏稳定后加载，不阻塞页面交互。
- 检查第三方脚本，能按操作加载的不得进入公共首屏包。

### 阶段 5：Preview 与正式发布验证

- 本地生产构建和浏览器测试通过后发布 Preview。
- Preview 使用正式数据库和正式支付配置，但不执行真实扣款；只验证登录、会话、页面导航和 Stripe 收银台打开。
- Preview 验证无回归后发布正式环境。
- 正式发布后同时对正式域名和 `workers.dev` 采样，以区分代码回归与网络链路波动。

## 7. 缓存与一致性

- 公共内容优先使用静态生成或可控的边缘缓存，缓存键至少包含语言和路由参数。
- 账户、余额和购买状态不得进入公共页面缓存；这些信息由独立动态请求获取。
- D1 继续作为线上数据库，不重新引入废弃的 `DATABASE_URL`。
- 内容更新后按现有再验证机制刷新，不以关闭所有缓存作为一致性手段。
- 对用户状态请求设置明确的加载、未登录和失败状态，失败时不能阻塞公共页面展示。

## 8. 错误与降级策略

- JavaScript 未加载：页面主体、主导航目标和关键说明仍可见；需要客户端能力的按钮显示可理解的等待或重试状态。
- 会话请求失败：公共内容照常展示，账户区退化为登录入口，不清空整个导航。
- 动态模块加载失败：在局部弹窗区域提供重试，不触发整页刷新或白屏。
- 图片失败：保留尺寸占位和替代文本，避免布局跳动。
- 支付 SDK 加载失败：提示用户重试，不创建重复订单。

## 9. 测试与验证

### 9.1 自动化测试

- 单元测试覆盖账户孤岛的已登录、未登录、加载和失败状态。
- 浏览器测试覆盖首页、图片提示词、动画提示词、详情、定价和创建页面。
- 在阻断全部 Next.js chunk 时验证主体内容仍可见。
- 在人为延迟 chunk 时连续切换导航，验证当前页面保持、pending 可见且最终只到达最后一次有效目标。
- 检查核心路由 HTML 和 JavaScript 体积预算。

### 9.2 功能回归

- 本地完成邮箱/OAuth 登录、退出和登录成功后导航状态更新。
- 本地测试单次购买和订阅完整 Stripe 流程，包括成功、取消和 webhook 后状态更新。
- 验证中文语言下仅显示微信支付按钮且不显示具体人民币价格；其他语言不显示微信支付入口。
- Preview 和正式环境只验证收银台能打开，不执行线上真实支付。
- 验证管理员、下载、生成、余额及历史记录功能按需加载后可正常使用。

### 9.3 性能验收

- 使用相同 Chrome 配置分别测量本地生产构建、Preview、`workers.dev` 和正式域名。
- 每条路由至少记录一次冷缓存和三次热缓存结果，使用中位数判断回归。
- 以 `workers.dev` 和本地生产构建判断代码性能；正式域名结果单独标注 DNS、连接、TTFB 和资源下载耗时。
- 验收报告必须同时包含优化前后体积和时序数据，不能只凭主观感受判定。

## 10. 发布与回滚

- 每个阶段保持可独立部署，优先发布不改变业务行为的组件边界与动态加载改造。
- Preview 至少完成核心页面无 JS、慢网导航、登录态和收银台打开验证。
- 正式发布后若出现登录、支付、页面主体不可见或导航白屏，立即回滚到上一个 Worker 版本。
- 若仅正式域名变慢而 `workers.dev`、版本号和资源哈希一致，则保留当前应用版本并按网络链路问题处理，避免反复回滚代码。

## 11. 风险与缓解

- **Server/Client 边界调整导致状态不同步**：账户状态通过单一接口和明确缓存策略读取，登录成功后只刷新账户孤岛或当前路由。
- **动态加载造成首次点击延迟**：对高频入口使用 hover/focus 预加载，并提供立即可见的局部 loading 状态。
- **减少首屏数据影响 SEO**：SEO 主体、结构化数据和首屏文本仍由服务端输出，只延后非关键交互与次级列表。
- **国际化消息遗漏**：按路由和组件建立消息键测试，覆盖中英文及微信支付特例。
- **过度追求体积破坏功能**：性能预算与功能回归共同作为发布门槛，任何支付、登录或内容回归均优先阻断发布。
- **跨境链路掩盖优化收益**：以本地生产构建和 `workers.dev` 作为应用基线，正式域名单独拆解网络阶段。

## 12. 完成标准

只有同时满足以下条件才视为完成：

- 核心页面在禁用 JavaScript 时可见且无白屏。
- 创建页初始 HTML 小于 500 KB；其余核心页面达到 200 KB 左右且不超过约定上限。
- 核心路由首屏 JavaScript 压缩体积不超过 150 KB，按需模块不进入首屏包。
- `workers.dev` 冷启动核心页面可见时间不超过 3 秒，热缓存不超过 2 秒；异常结果有可复现的网络或 Worker 冷启动证据。
- 导航慢网测试、全量单元测试和生产构建全部通过。
- 登录成功后登录按钮正确更新为账户状态。
- 本地 Stripe 单次购买、订阅和 webhook 流程通过，Preview/正式收银台可正常打开。
- 中文微信支付展示规则保持不变。
- Preview 验证通过后才允许正式发布，并保留可快速回滚的上一 Worker 版本。
